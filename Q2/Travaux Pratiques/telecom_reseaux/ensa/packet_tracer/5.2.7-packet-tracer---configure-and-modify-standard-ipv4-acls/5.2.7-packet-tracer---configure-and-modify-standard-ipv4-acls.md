## Objectifs

- **Partie 1 :** Vérifier la connectivité initiale

---

## Contexte

Ce lab consolide les ACLs standard numérotées et nommées dans un même réseau, et introduit la **modification d'une ACL nommée en place** par numéro de séquence — technique essentielle pour éviter de réécrire une ACL entière à chaque changement de politique.

```
PC-A> ping 192.168.30.3   (PC-C)
```

**Réponses :** Tous les pings réussissent. Le serveur `209.165.200.254` est également joignable depuis tous les PCs. C'est la baseline avant toute ACL.

## Partie 2 : Configurer les ACLs standard

### Étape 1 : ACL numérotée sur R3

**Politique :**
> Permettre l'accès au réseau `192.168.30.0/24` uniquement aux réseaux `192.168.10.0/24` et `192.168.20.0/24`. Tout autre trafic est bloqué. Un `deny any` explicite doit terminer toute ACL.

**Réponses aux questions de planification :**

- **Wildcard pour `192.168.10.0/24` ?** → `0.0.0.255`
- **Sur quel routeur ?** → **R3** (le plus proche de la destination `192.168.30.0/24`)
- **Interface et direction ?** → **G0/0/0 outbound** (interface de R3 vers PC-C)

#### Configuration

```
R3(config)# access-list 1 remark Allow R1 LANs Access
R3(config)# access-list 1 permit 192.168.10.0 0.0.0.255
R3(config)# access-list 1 permit 192.168.20.0 0.0.0.255
R3(config)# access-list 1 deny any
```

```
R3(config)# interface g0/0/0
R3(config-if)# ip access-group 1 out
```

> **`remark`** : commentaire associé à l'ACL, visible dans `show access-lists` et `show run`. N'affecte pas le filtrage — sert uniquement à la documentation.

#### Vérification

**Réponses aux questions :**
- **Commande pour voir l'ACL complète ?** → `show access-lists 1`
- **Commande pour voir où elle est appliquée ?** → `show ip interface g0/0/0`

```
R3# show access-lists 1
Standard IP access list 1
    permit 192.168.10.0, wildcard bits 0.0.0.255
    permit 192.168.20.0, wildcard bits 0.0.0.255
    deny any

R3# show ip interface g0/0/0
...
    Outgoing access list is 1
    Inbound access list is not set
```

#### Tests de l'ACL numérotée

| Source | Destination | Résultat | Raison |
|--------|-------------|----------|--------|
| PC-A (`192.168.10.3`) | PC-C (`192.168.30.3`) | ✅ | `permit 192.168.10.0` matche |
| PC-B (`192.168.20.3`) | PC-C (`192.168.30.3`) | ✅ | `permit 192.168.20.0` matche |
| PC-D (`192.168.40.3`) | PC-C (`192.168.30.3`) | ❌ | `deny any` — `192.168.40.x` non listé |
| R1 (`192.168.10.1` ou `192.168.20.1`) | PC-C (`192.168.30.3`) | ❌ | **Voir explication ci-dessous** |

> **Pourquoi R1 ne peut-il pas pinger PC-C ?** Quand R1 lance un ping vers `192.168.30.3`, le paquet ICMP a pour adresse source l'**interface de sortie de R1** vers le réseau concerné — soit `10.1.1.1` (S0/1/0, le lien vers Edge). Cette adresse n'est ni dans `192.168.10.0/24` ni dans `192.168.20.0/24` → `deny any` → ping échoue. Un ping depuis les PCs fonctionne car l'adresse source est bien dans les plages autorisées.

### Étape 2 : ACL nommée sur R1

**Politique :**
> Permettre l'accès au réseau `192.168.10.0/24` uniquement à :
> - PC-C spécifiquement (`192.168.30.3`)
> - Tous les hôtes du réseau `192.168.40.0/24`

**Réponses aux questions de planification :**
- **Sur quel routeur ?** → **R1** (plus proche de la destination `192.168.10.0/24`)
- **Interface et direction ?** → **G0/0/0 outbound** (vers PC-A)

#### Configuration

```
R1(config)# ip access-list standard BRANCH-OFFICE-POLICY
R1(config-std-nacl)# permit host 192.168.30.3
R1(config-std-nacl)# permit 192.168.40.0 0.0.0.255
R1(config-std-nacl)# end
```

```
R1(config)# interface g0/0/0
R1(config-if)# ip access-group BRANCH-OFFICE-POLICY out
```

**Réponse — autre façon d'écrire `permit host 192.168.30.3` ?**
→ `permit 192.168.30.3 0.0.0.0` — le mot-clé `host` est un raccourci pour le wildcard `0.0.0.0`.

#### Vérification

```
R1# show access-lists
Standard IP access list BRANCH-OFFICE-POLICY
    10 permit host 192.168.30.3
    20 permit 192.168.40.0 0.0.0.255
```

**Réponse — différence avec l'ACL de R3 ?**
→ L'ACL de R1 (nommée) affiche les **numéros de séquence** (10, 20) dans `show access-lists`. L'ACL de R3 (numérotée) ne les affiche pas dans la sortie de Packet Tracer. En IOS réel, les deux affichent des numéros de séquence.

```
R1# show ip interface g0/0/0
...
    Outgoing access list is BRANCH-OFFICE-POLICY
```

#### Tests de l'ACL nommée

| Source | Destination | Résultat | Raison |
|--------|-------------|----------|--------|
| PC-C (`192.168.30.3`) | PC-A (`192.168.10.3`) | ✅ | `permit host 192.168.30.3` |
| PC-D (`192.168.40.3`) | PC-A (`192.168.10.3`) | ✅ | `permit 192.168.40.0/24` |
| R3 (source `192.168.30.1`) | PC-A (`192.168.10.3`) | ❌ | `192.168.30.1` ≠ `192.168.30.3` → deny implicite |

> **Extended ping depuis R3 :** La commande `ping` étendue permet de spécifier l'adresse source, simulant un paquet provenant de `192.168.30.1`. Résultat `U.U.U` (Unreachable) confirme que seul l'hôte `192.168.30.3` est autorisé, pas le réseau entier.

## Partie 3 : Modifier l'ACL BRANCH-OFFICE-POLICY

**Problème :** PC-A ne peut pas atteindre le serveur Internet `209.165.200.254`. Les réponses du serveur ont pour source `209.165.200.x` — cette adresse ne matche aucun `permit` dans BRANCH-OFFICE-POLICY → `deny any` implicite → trafic de retour bloqué.

**Nouvelle politique management :**
- Autoriser le réseau `209.165.200.224/27` à accéder à `192.168.10.0/24`
- Ajouter un `deny any` explicite en fin d'ACL (règle de cohérence sur tous les routeurs)

### Option 1 : Supprimer et réécrire (déconseillé)

Supprimer avec `no ip access-list standard BRANCH-OFFICE-POLICY`, puis tout réécrire. Risqué : peut supprimer temporairement le filtrage ou introduire des erreurs de frappe.

### Option 2 : Modifier en place (recommandé) ✅

```
R1(config)# ip access-list standard BRANCH-OFFICE-POLICY
R1(config-std-nacl)# 30 permit 209.165.200.224 0.0.0.31
R1(config-std-nacl)# 40 deny any
R1(config-std-nacl)# end
```

> **Wildcard pour `/27` :** `255.255.255.224` → inverse = `0.0.0.31`. Le réseau `209.165.200.224/27` couvre les adresses `209.165.200.224` à `209.165.200.255`.

> En spécifiant le numéro de séquence (`30`, `40`), on insère les nouvelles ACEs **à la fin** sans toucher aux ACEs 10 et 20 existantes. C'est l'avantage majeur des ACLs nommées.

#### Vérification finale

```
R1# show access-lists
Standard IP access list BRANCH-OFFICE-POLICY
    10 permit host 192.168.30.3          (8 matches)
    20 permit 192.168.40.0 0.0.0.255     (5 matches)
    30 permit 209.165.200.224 0.0.0.31
    40 deny any
```

**Réponse — faut-il réappliquer l'ACL sur G0/0/0 ?** → **Non.** L'ACL est déjà appliquée sur l'interface avec `ip access-group BRANCH-OFFICE-POLICY out`. La modification du contenu de l'ACL est automatiquement prise en compte — seul le **nom** crée le lien entre l'interface et l'ACL.

```
PC-A> ping 209.165.200.254
```
**Réussi** — les réponses du serveur (`209.165.200.x`) matchent maintenant la ligne 30.

## Réflexion

**1. Pourquoi utiliser des ACLs étendues ?**

Les ACLs standard ne filtrent que sur **l'adresse source**. Pour filtrer sur la destination, le protocole (TCP/UDP/ICMP), ou les ports (HTTP=80, SSH=22, etc.), il faut une **ACL étendue**. Exemple : autoriser PC-A à accéder au web (port 80) mais pas au FTP (port 21) sur le même serveur — impossible avec une ACL standard.

**2. Pourquoi choisir des ACLs nommées malgré plus de frappe ?**

- **Lisibilité** : `BRANCH-OFFICE-POLICY` est immédiatement compréhensible, `access-list 1` ne l'est pas
- **Modifiabilité** : ajout/suppression d'ACEs individuelles sans réécrire toute la liste
- **Documentation** : le nom sert de commentaire intégré dans la configuration

## Tableau récapitulatif des commandes clés

| Commande | Contexte | Description |
|----------|----------|-------------|
| `access-list <num> remark <texte>` | Global config | Ajoute un commentaire à une ACL numérotée |
| `access-list <num> permit/deny <src> <wc>` | Global config | ACL numérotée standard |
| `ip access-list standard <nom>` | Global config | Crée/modifie une ACL nommée |
| `<seq> permit/deny <src> <wc>` | ACL config | ACE avec numéro de séquence explicite |
| `no <seq>` | ACL config | Supprime une ACE par son numéro de séquence |
| `ip access-group <nom/num> {in\|out}` | Interface config | Applique l'ACL |
| `show access-lists [<num/nom>]` | Privileged EXEC | Affiche l'ACL et les compteurs |
| `show ip interface <if>` | Privileged EXEC | Vérifie quelle ACL est appliquée |
| `ping` étendu (routeur) | Privileged EXEC | `ping` → `y` aux extended commands → spécifier source |

---

## Mémo — Modification d'ACL nommée en place

```
Ajouter une ACE à la fin :
  ip access-list standard <NOM>
    <numéro_séq> permit/deny ...   ← numéro > dernier existant

Supprimer une ACE existante :
  ip access-list standard <NOM>
    no <numéro_séq>

Insérer une ACE entre deux existantes :
  ip access-list standard <NOM>
    <numéro_entre_les_deux> permit/deny ...
  Ex: entre séq 10 et 20 → utiliser séq 15

Pas besoin de réappliquer l'ACL sur l'interface après modification.
```

## Script complet

```
! ============================================================
! PARTIE 2 - ACL numérotée sur R3
! ============================================================

! --- Sur R3 ---
      access-list 1 remark Allow R1 LANs Access
      access-list 1 permit 192.168.10.0 0.0.0.255
      access-list 1 permit 192.168.20.0 0.0.0.255
      access-list 1 deny any

      interface g0/0/0
        ip access-group 1 out

! --- Vérification R3 ---
  show access-lists 1
  show ip interface g0/0/0

! ============================================================
! PARTIE 2 - ACL nommée sur R1
! ============================================================

! --- Sur R1 ---
      ip access-list standard BRANCH-OFFICE-POLICY
        permit host 192.168.30.3
        permit 192.168.40.0 0.0.0.255

      interface g0/0/0
        ip access-group BRANCH-OFFICE-POLICY out

! --- Vérification R1 ---
  show access-lists
  show ip interface g0/0/0

! ============================================================
! PARTIE 3 - Modification de l'ACL nommée sur R1
! ============================================================

! --- Sur R1 : ajout des ACEs 30 et 40 ---
      ip access-list standard BRANCH-OFFICE-POLICY
        30 permit 209.165.200.224 0.0.0.31
        40 deny any

! --- Vérification finale ---
  show access-lists

! --- Test depuis PC-A ---
ping 209.165.200.254
```
