# Packet Tracer – Configure and Verify NTP

## Topologie

| Device | Interface | Adresse IP      | Masque de sous-réseau | Rôle NTP |
|--------|-----------|-----------------|-----------------------|----------|
| N1     | NIC       | 209.165.200.225 | 255.255.255.0         | **Serveur NTP** (Stratum 1) |
| R1     | G0/0      | 209.165.200.226 | 255.255.255.0         | **Client NTP** |
| R2     | G0/0      | 209.165.200.227 | 255.255.255.0         | **Client NTP** |

---

## Objectifs

Configurer R1 et R2 comme clients NTP pointant vers le serveur N1, et vérifier la synchronisation de l'horloge.

---

## Contexte

**NTP (Network Time Protocol)** synchronise l'heure sur tous les équipements réseau. C'est un prérequis fondamental pour :
- **La corrélation des logs** : si deux routeurs ont des horloges désynchronisées, relier un événement sur R1 à un événement sur R2 devient impossible (timestamps incohérents)
- **Les certificats TLS/SSL** : les certificats ont des dates de validité — une horloge incorrecte invalide les connexions HTTPS
- **Les protocoles de sécurité** (Kerberos, IPsec) qui dépendent d'une référence de temps commune
- **Les ACLs time-based** et les planifications de tâches

**Transport :** UDP port 123. **Référence :** UTC (Coordinated Universal Time).

**Concept de Stratum :** NTP organise les sources de temps en niveaux (strata) :

```
Stratum 0 : Source de temps atomique / GPS (horloge de référence)
Stratum 1 : Serveur directement connecté à une source Stratum 0 (N1 dans ce lab)
Stratum 2 : Équipement synchronisé sur un Stratum 1 (R1 et R2 dans ce lab)
Stratum 3 : Synchronisé sur Stratum 2... etc.
(jusqu'à Stratum 15 — Stratum 16 = non synchronisé)
```

> Plus le stratum est bas, plus la source est précise. Un équipement cherche toujours à se synchroniser sur la source de stratum le plus bas disponible.

## Étape 1 : Serveur NTP (N1 — déjà configuré)

N1 est préconfigurée comme serveur NTP dans Packet Tracer (Services → NTP).

**Vérification de connectivité :**

```
R1# ping 209.165.200.225
R2# ping 209.165.200.225
```

Les deux pings doivent réussir — prérequis à la synchronisation NTP.

---

## Étape 2 : Configurer R1 et R2 comme clients NTP

### État initial (avant NTP)

```
R1# show ntp status
%NTP is not enabled.

R1# show clock detail
*0:1:53.745 UTC Mon Mar 1 1993
Time source is hardware calendar
```

> L'astérisque `*` devant l'heure indique que l'horloge **n'est pas synchronisée** (elle est approximative). La source `hardware calendar` signifie que le routeur utilise son RTC (Real-Time Clock) interne — qui dérive dans le temps et n'est pas fiable.

### Configuration des clients NTP

```
R1(config)# ntp server 209.165.200.225
```

```
R2(config)# ntp server 209.165.200.225
```

> **`ntp server <IP>`** désigne l'adresse du serveur NTP à contacter. R1 et R2 envoient des requêtes NTP (UDP 123) vers N1 pour se synchroniser. La commande peut être répétée avec plusieurs IPs pour redondance.

---

## Étape 3 : Vérifier la synchronisation NTP

### Vérifier l'heure synchronisée

```
R1# show clock detail
12:7:18.451 UTC Sat Oct 12 2019
Time source is NTP
```

> La disparition de l'astérisque et l'apparition de `Time source is NTP` confirment la synchronisation réussie. L'heure correspond maintenant à la référence UTC de N1.

**Réponse — Les horloges sont-elles synchronisées ?** → **Oui.** R1 et R2 affichent la même heure UTC, synchronisée sur N1. Dans Packet Tracer, utiliser **Fast Forward Time** pour accélérer le processus (sur équipement physique : attendre 1–3 minutes).

### Vérifier le statut NTP

```
R1# show ntp status
Clock is synchronized, stratum 2, reference is 209.165.200.225
```

**Lecture de la sortie :**

| Champ | Valeur | Signification |
|-------|--------|---------------|
| `Clock is synchronized` | — | Synchronisation réussie |
| `stratum 2` | 2 | R1 est à 2 niveaux de la source atomique (N1 est Stratum 1) |
| `reference is 209.165.200.225` | IP de N1 | Serveur NTP de référence utilisé |

### Vérifier les associations NTP

```
R1# show ntp associations
address         ref clock       st  when  poll  reach  delay  offset  disp
*~209.165.200.225 127.127.1.1    1   11    32    377    9.00   4.00   0.24
* sys.peer, # selected, + candidate, - outlyer, x falseticker, ~ configured
```

**Lecture des colonnes :**

| Colonne | Valeur | Signification |
|---------|--------|---------------|
| `*` (préfixe) | — | Ce serveur est le **sys.peer** — la source de temps actuellement utilisée |
| `~` (préfixe) | — | Ce serveur est **configuré** (via `ntp server`) |
| `address` | `209.165.200.225` | IP du serveur NTP |
| `ref clock` | `127.127.1.1` | Référence de N1 (horloge locale interne — source Stratum 0 simulée) |
| `st` | `1` | Stratum du serveur (N1 = Stratum 1) |
| `when` | `11` | Secondes depuis le dernier paquet reçu |
| `poll` | `32` | Intervalle de polling en secondes |
| `reach` | `377` | Registre d'accessibilité (377 octal = 11111111 binaire = 8 réponses reçues consécutives = synchro stable) |
| `delay` | `9.00` | Délai aller-retour en ms |
| `offset` | `4.00` | Décalage d'horloge mesuré en ms |

## Tableau récapitulatif des commandes clés

| Commande | Contexte | Description |
|----------|----------|-------------|
| `ntp server <IP>` | Global config | Désigne un serveur NTP (le routeur devient client) |
| `ntp master [stratum]` | Global config | Configure le routeur comme serveur NTP autoritaire |
| `show ntp status` | Privileged EXEC | État de synchronisation, stratum, référence |
| `show ntp associations` | Privileged EXEC | Détails des associations NTP (polling, offset, reach) |
| `show clock detail` | Privileged EXEC | Heure actuelle + source (NTP, hardware calendar, manual) |
| `clock set <hh:mm:ss> <day> <month> <year>` | Privileged EXEC | Régler l'heure manuellement (sans NTP) |

## Mémo — NTP

```
Client NTP (routeur/switch se synchronise sur un serveur) :
  ntp server <IP_serveur>
  → Le device devient Stratum (serveur + 1)

Serveur NTP autoritaire (le routeur distribue l'heure à d'autres) :
  ntp master 1        ← Stratum 1 (source locale)
  ntp master 2        ← Stratum 2 etc.
  → Utile si pas d'accès à un serveur NTP externe

Vérification :
  show ntp status      → synchronized / not synchronized, stratum, référence
  show ntp associations → * = sys.peer (source active), ~ = configuré
  show clock detail    → heure + source (NTP = ok, hardware calendar = non sync)

Stratum dans show ntp associations :
  reach = 377 (octal) → toutes les 8 dernières requêtes ont reçu réponse → stable
  reach = 0           → aucune réponse reçue → problème de connectivité

Importance de NTP pour les logs :
  Sans NTP : timestamp logs = heure locale non fiable → corrélation impossible
  Avec NTP : tous les devices partagent le même UTC → analyse forensique cohérente
```
