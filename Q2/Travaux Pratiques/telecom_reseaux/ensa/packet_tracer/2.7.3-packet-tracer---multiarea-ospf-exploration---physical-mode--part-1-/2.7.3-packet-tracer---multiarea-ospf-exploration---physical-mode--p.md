## Contexte

Ce lab est un **lab d'exploration** — pas de configuration à réaliser dans cette partie. L'objectif est d'observer et de comprendre les **limites du single-area OSPF** lorsque le réseau grandit, notamment l'impact des changements de topologie sur le nombre d'exécutions de l'algorithme SPF.

**Problématique centrale :** En single-area OSPF, **tout changement topologique** (panne d'interface, nouveau lien, routeur qui tombe) oblige **chaque routeur du domaine entier** à relancer l'algorithme SPF — même ceux qui sont dans des bâtiments distants et non affectés par le changement. Sur un petit réseau, c'est négligeable. Sur un grand réseau, cela peut saturer les CPU et dégrader les performances.

## Partie 1 : Évaluer le fonctionnement du Single-Area OSPF

### Étape 1 : Exploration dans le Corporate HQ (B1_R4 et B1_R2)

#### a–d. Navigation et vérification des adjacences

Après ouverture du fichier PT, naviguer jusqu'au **Sao Paulo HQ Wiring Closet** et ouvrir la CLI de **B1_R4**. La console confirme 4 adjacences FULL établies :

```
%OSPF-5-ADJCHG: Process 1, Nbr 172.17.1.1   on G0/0/1 from LOADING to FULL
%OSPF-5-ADJCHG: Process 1, Nbr 192.168.2.1  on G0/0/0 from LOADING to FULL
%OSPF-5-ADJCHG: Process 1, Nbr 192.168.1.1  on G0/0/0 from LOADING to FULL
%OSPF-5-ADJCHG: Process 1, Nbr 192.168.3.1  on G0/0/0 from LOADING to FULL
```

> B1_R4 est connecté à G0/0/0 (segment multi-accès HQ — 3 voisins) et G0/0/1 (lien vers Branch Office via B1_R5 → B2_R5).

#### e. Table de routage — `show ip route`

```
B1_R4# show ip route
```

La table contient **toutes les routes du réseau entier** : réseaux HQ (192.168.x.x) ET réseaux Branch Office (10.10.x.x, 10.20.x.x) — tous appris via OSPF (code `O`). C'est la caractéristique du single-area : **chaque routeur connaît la topologie globale complète**.

#### f. Nombre d'exécutions SPF — `show ip ospf`

```
B1_R4# show ip ospf
```

**Réponses aux questions :**

- **Nombre d'exécutions SPF :** La valeur affichée dans `Number of times SPF algorithm executed` correspond aux recalculs effectués depuis le démarrage. Noter cette valeur de référence.
- **Nombre d'areas affichées :** **1** — toute la topologie est dans Area 0.

#### g. Même vérification sur B1_R2

```
B1_R2# show ip route
B1_R2# show ip ospf
```

**Observation :** B1_R2 (HQ, bâtiment 1) a **exactement la même table de routage** que B1_R4 concernant les routes OSPF. Il connaît les réseaux du Branch Office (`10.10.x.x`) alors qu'il n'y est pas directement connecté — c'est la LSDB commune à toute l'area qui lui fournit ces informations.

**Réponse :** Le compteur SPF de B1_R2 est identique ou très proche de celui de B1_R4 — les deux ont recalculé SPF le même nombre de fois car ils partagent la même area.

### Étape 2 : Exploration dans le Branch Office (B2_R3, puis simulation de panne)

#### d–g. B2_R3 — adjacences et table de routage

Naviguer jusqu'au **Sao Paulo Branch Office Wiring Closet**, CLI de **B2_R3** :

```
%OSPF-5-ADJCHG: Process 1, Nbr 2.2.2.2 on G2/0 from LOADING to FULL
%OSPF-5-ADJCHG: Process 1, Nbr 4.4.4.4 on G1/0 from LOADING to FULL
```

```
B2_R3# show ip route
B2_R3# show ip ospf
```

**Réponses aux questions :**

- **Nombre d'exécutions SPF :** Même ordre de grandeur que B1_R4 et B1_R2 — tous les routeurs ont recalculé autant de fois.
- **Nombre d'areas :** **1** — identique, Area 0 unique.

**Observation clé :** La table de routage de B2_R3 (Branch Office) contient les mêmes routes que celle de B1_R4 (HQ) — y compris les réseaux `192.168.x.x` du HQ qu'il ne desservira probablement jamais directement. En single-area, **tout le monde sait tout**.

#### i. Simulation de panne : extinction de B2_R1

Sur **B2_R1**, onglet **Physical** → éteindre le routeur. Cela rend les réseaux `10.10.0.8/30` et `10.10.0.16/30` injoignables.

Attendre ~40 secondes (dead timer) puis vérifier sur un routeur HQ et un routeur Branch Office :

```
show ip route
show ip ospf
```

**Réponse à la question :**

- **Les deux réseaux ont-ils disparu des tables de routage, et le compteur SPF a-t-il augmenté ?** → **Oui, sur TOUS les routeurs** — HQ et Branch Office confondus. Chaque routeur du domaine entier a relancé SPF, y compris B1_R2 (HQ) qui n'a aucune relation directe avec B2_R1.

> **C'est le problème fondamental du single-area à grande échelle** : la panne d'un routeur dans le Branch Office force les routeurs du HQ à recalculer SPF — et vice versa. Chaque événement topologique se propage à l'ensemble du domaine OSPF.

## Synthèse — Limites du Single-Area OSPF

```
Single-Area OSPF : tout le réseau dans Area 0

Avantages :
  └─ Simple à configurer et à administrer
  └─ Convergence rapide sur petits réseaux

Problèmes à grande échelle :
  ┌─ Toute panne → SPF recalculé sur CHAQUE routeur du domaine
  ├─ Tables de routage volumineuses (chaque routeur connaît tous les réseaux)
  ├─ LSDB grande → plus de mémoire consommée
  └─ Beaucoup de trafic LSA en cas de topologie instable

Solution : Multiarea OSPF
  └─ Les changements dans une area n'affectent pas le SPF des autres areas
  └─ Les ABR (Area Border Routers) résument les routes entre areas
  └─ Réduction de la taille des LSDB et des tables de routage par area
```
